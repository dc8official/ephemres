# Release Notes: Ephemres v3.3.5

**Release Tag**: `v3.3.5`  
**Target Architecture**: Vertical Integration Architecture — Traffic Analytics, Probe History, WAN Edge Totals & NetFlow Route Augmentation  
**Release Date**: October 2026  
**Repository**: `https://github.com/dc8official/ephemres.git`  

---

## Executive Summary

Ephemres `v3.3.5` builds directly upon the zero-dependency **Vertical Integration Architecture** introduced in `v3.3.2.v` (running on the Python 3.11+ Standard Library plus `uvicorn` and `asyncpg`), delivering a comprehensive upgrade across passive flow analytics, active ICMP probe telemetry, WAN edge capacity accounting, NetFlow-assisted route discovery, and operator dashboard ergonomics:

1. **NetFlow Route Discovery & Topology Verification**: Decodes IPv4/IPv6 next-hop addresses from NetFlow v5, NetFlow v9, and IPFIX (`flow_path_observations`), detects sustained routing shifts vs. ECMP load-balancing (`flow_route_changes`), triggers targeted re-traceroutes (`ROUTE_HINT`) for `UP` endpoints, verifies topology links (`confirmed`, `differs`, `inferred` silent `* * *` hops), and attaches flow evidence to Root Cause Analysis (RCA) incidents.
2. **WAN Interface Roles & Network Edge Totals**: Introduces `"wan"` / `"lan"` interface roles so multi-router networks can measure true network-edge ingress/egress once at the perimeter (`services/wan_edge.py`, `wan_only=true` traffic series, and WAN link breakdown cards) alongside per-exporter sums.
3. **Per-Cycle Probe History & Sub-Cycle Telemetry**: Captures per-cycle minimum, average, maximum RTT, jitter, and packet loss into a dedicated `endpoint_probe_samples` TimescaleDB hypertable (30-day retention, compressed after 2 days) and `endpoint_probe_hourly` continuous aggregate (365-day retention), powering real loss percentages, 95th-percentile RTT, dashboard sparklines, min/max latency bands, and shared-axis Latency vs. Bandwidth correlation.
4. **Traffic Analytics & Honest Telemetry Mathematics**: Consolidates all flow rate, utilization, DSCP, zone, and TCP anomaly calculations into `app.services.flow_metrics` (shared by the REST API and PDF report compiler), separates pure transit traffic (`transit_bps` / `transit_pps`) from endpoint ingress/egress, enables real-time continuous aggregates (`materialized_only = false`), adds hourly interface rollups (`flow_interface_hourly_rollups`) with p95/peak utilization, and introduces server-side filtered and paginated conversation forensics (`GET /api/v1/bandwidth/conversations`).

## Version Support & Lifecycle Update

With the release of `v3.3.5`, the Ephemres support matrix is updated as follows:
* **`v3.3.5` (Current Standard)**: Active production release incorporating all `v3.3.2.v` zero-dependency engines plus Traffic Analytics, Per-Cycle Probe History, WAN Edge Totals, and NetFlow Route Augmentation.
* **`v3.3.2.v` (Supported Production Release)**: Remains supported and safe for production operation. Upgrading to `v3.3.5` is recommended for enhanced flow accuracy, probe history, and route discovery.
* **`v3.3.0` (Enterprise LTS)**: Designated Long-Term Support (LTS) maintenance track.
* **`v3.1.35s` (End of Support)**: No longer supported. Operators running `v3.1.35s` should upgrade to `v3.3.0` (LTS) or directly to `v3.3.5` using the automated upgrade and cross-version restore tooling.

## Key Architectural & Feature Highlights

### 1. NetFlow Route Discovery & Topology Augmentation (Migration `0017`)
Traceroute remains the route of record for baseline topology and RCA verdicts, while NetFlow/IPFIX now supplies continuous visibility into where real production traffic is forwarded every minute:
* **Next-Hop Decoding (`monitoring/flow/*_parser.py`)**: Extracts the forwarding next hop across NetFlow v5 (`nexthop`), NetFlow v9 (fields `15` `IPV4_NEXT_HOP` and `62` `IPV6_NEXT_HOP`), and IPFIX (IE `15` `ipNextHopIPv4Address` and `62` `ipNextHopIPv6Address`). Local delivery (`0.0.0.0` / `::`) and omitted fields normalize to `NULL`.
* **Forwarding Path Observations (`flow_path_observations`)**: Records each distinct `(exporter_id, endpoint_id, direction, in_if, out_if, next_hop)` tuple with `first_seen`, `last_seen`, cumulative `bytes`, and `flow_count` (pruned after 30 days of inactivity).
* **Sustained Route Change Detector & ECMP Awareness (`monitoring/flow/path_tracker.py`)**: Evaluates arrival-minute dominant paths per `(exporter, endpoint, direction)`. Distinguishes multi-path ECMP load-balancing (paths each carrying $\ge 20\%$ of bytes, configurable via `[flow] route_ecmp_share`) from genuine routing shifts. When a new path dominates for $N$ consecutive minutes (default `3`, `[flow] route_change_minutes`) and the old path stops carrying traffic, records a row in `flow_route_changes` (90-day retention) and publishes a `ROUTE_HINT` event.
* **Targeted Traceroute Refresh (`backend/app/services/telemetry_relay.py`)**: On `ROUTE_HINT`, the leader API worker queues an immediate background traceroute for the affected endpoint if it is `UP` and has `enable_scheduled_discovery` enabled, guarded by a 15-minute per-endpoint cooldown and a 10-traces/minute global cap.
* **Topology Link Verification (`backend/app/services/flow_paths.py`, `topology.py`)**: Every 5 minutes (and across topology rebuilds), baseline traceroute edges are compared against recent flow observations (last 15 minutes):
  * `confirmed`: Active flow next hop matches the next traceroute hop.
  * `differs`: Traffic is forwarded to a different next hop than the baseline traceroute path.
  * `inferred`: Next traceroute hop is anonymous (`* * *`), and flow data supplies the router IP (`flow_inferred_ip`).
* **RCA Flow Evidence (`endpoint_rca_incidents.flow_evidence`)**: When an outage triggers RCA, Ephemres snapshots recent forwarding paths, route changes within 15 minutes prior to failure, and whether traffic continued flowing after ICMP probes began failing (`traffic_after_failure`).

### 2. WAN Interface Role & Network Edge Totals (`backend/app/services/wan_edge.py`)
In networks with multiple exporting routers, summing ingress/egress across all exporters counts packets once per router traversed. `v3.3.5` introduces explicit WAN perimeter accounting:
* **WAN / LAN Interface Roles**: Each entry in `endpoints.flow_interface_aliases` supports `role: "wan" | "lan"` (default `"lan"`), configurable from both the Traffic Analytics and Endpoint Detail interface modals.
* **Network Edge KPIs & Link Breakdown**: `GET /api/v1/bandwidth/overview` computes `wan_interfaces_count`, `wan_in_bps`, `wan_out_bps`, `wan_in_pps`, `wan_out_pps`, and per-link `wan_links` (rates, utilization, and share of WAN volume).
* **Edge Time Series (`wan_only=true`)**: `GET /api/v1/bandwidth/traffic-series?wan_only=true` aggregates traffic strictly across WAN-role interfaces so each packet entering or leaving the network is counted once.
* **Traffic Counted Once per Conversation**: Traffic that crosses several exporting routers is reported by each of them. An endpoint's traffic chart, applications, QoS and zones, and conversations and top talkers everywhere, now count each conversation once per minute, taking the largest report among the routers that saw it, instead of adding the reports up (two exporting routers showed an endpoint's traffic twice). A single router's own view still shows everything it exported. Fleet-wide totals and charts keep using the WAN interfaces above.

### 3. Per-Cycle Probe History & Interface Hourly Rollups (Migrations `0014`–`0016`)
* **Real-Time Continuous Aggregates (`0014_realtime_flow_aggregates.py`)**: Enables `materialized_only = false` on `flow_hourly_rollups` and `flow_daily_rollups` so `24h`, `7d`, and `30d` traffic charts include the most recent unmaterialized minutes.
* **Per-Cycle Probe Samples (`0015_endpoint_probe_samples.py`)**: Extends `PingResult` with `rtt_min_ms`, `rtt_max_ms`, and `jitter_ms`, writing every 60-second sweep cycle into the `endpoint_probe_samples` hypertable (compressed after 2 days, retained 30 days) with an hourly continuous aggregate `endpoint_probe_hourly` (retained 365 days).
* **Probe Summary & Series Endpoints**: Adds `GET /api/v1/endpoints/probe-summary` (fleet-wide 24h loss %, average/p95 RTT, jitter, hourly sparklines) and `GET /api/v1/endpoints/{id}/probe-series` (adaptive resolution: per-cycle up to 2d, 10-minute buckets up to 8d, hourly up to 365d).
* **Interface Hourly Rollups & Percentile Utilization (`0016_flow_interface_hourly_rollups.py`)**: Adds `flow_interface_hourly_rollups` tracking hourly byte/packet sums plus busiest-minute peaks (`peak_in_minute_bytes`, `peak_out_minute_bytes`, 365-day retention). `GET /api/v1/bandwidth/interfaces` now reports average, 95th-percentile (`p95`), and busiest-minute (`peak`) utilization, and returns `speed_configured: false` with `null` utilization when an interface has no configured link speed.

* **"In State Since" Survives Splits and Restarts (`0019_endpoint_event_state_since.py`)**: A state period is closed every 24 hours and on every engine restart, so "In state since" used to restart from the latest of them ("UP for 3 hours" for an endpoint up for weeks). The engine now carries the start of the unbroken state on the new row (`endpoint_events.state_since`) and the dashboard, endpoint list and drawer show it. The audit log keeps the separate rows. Rows written before the upgrade don't carry it, so for a state that began before the upgrade the count goes back only to its last 24-hour split before the upgrade.

* **Wider Aggregate Refresh Windows (`0018_wider_aggregate_refresh_windows.py`)**: Refresh policies now reach back 29 days (`endpoint_probe_hourly`, `flow_hourly_rollups`) and 60 days (`flow_daily_rollups`) instead of 3/3/7, inside each source's and aggregate's retention. Hours missed while the TimescaleDB job scheduler was stopped are filled in when it resumes instead of leaving permanent gaps; a normal hourly refresh costs the same.

### 4. Traffic Analytics, Server-Side Conversations & UI Ergonomics
* **Audit Log Period Figures**: A closed period in the audit log now carries the health and average latency of the whole period. Before, it kept its last minute's: an UP period that ended in an outage showed 0 % health and no latency. Periods recorded before the upgrade can be corrected with an optional tool, `sudo /opt/ephemres/deploy/repair-audit-history.sh` (reports first, writes only with `--apply`); the upgrade points to it when there is something to correct. See [Troubleshooting, section L](../troubleshooting.md).
* **Engine Downtime Left Out of Availability**: Time the monitoring engine is not running (stop, crash, reboot, upgrade) is now recorded as a monitoring gap and left out of uptime %, as the SLA calculation always intended; the code that should have recorded it was never called. On start, each period left open is closed at its last probe cycle instead of at the start time. See [SLA calculation](../sla-calculation.md). History from before the upgrade has no gap records and keeps its figures; the upgrade's own downtime is the first gap recorded.
* **Long PDF Bandwidth Reports**: Interface and WAN figures in a report reaching back more than 7 days now come from the hourly interface rollup (kept 365 days, with each hour's busiest minute). They used to come from the minute table, which is kept 7 days, so a 30-day report showed one week of traffic averaged over 30 days.
* **Endpoint Flow Tab**: Devices that don't export flows open their Bandwidth & Flow tab on "As participant" (their own traffic) instead of the empty "As exporter" view.
* **Single Source of Flow Math (`backend/app/services/flow_metrics.py`)**: Unifies rate calculation, utilization clamping, interface alias normalization, DSCP class bucketing, traffic zone classification, and TCP flag anomaly rules (`tcp_anomaly_sql`) across `routers/bandwidth.py` and `services/report_compiler.py`.
* **Honest Transit & SLA Accounting**:
  * Flows where neither source nor destination is a monitored endpoint are reported as `transit_bps` / `transit_pps` instead of being split 50/50 into ingress and egress.
  * Passive flow exporters and paused endpoints (`monitoring_enabled = false`) are placed in a dedicated **"Not monitored"** bucket and excluded from Fleet SLA percentages, report uptime durations, and PDF executive averages.
* **Server-Side Conversation Forensics (`GET /api/v1/bandwidth/conversations`)**: Filters (`ip`, `port`, `dscp`, `quick`: `all` | `anomalies` | `qos` | `bulk`), counts, sorts (`bytes` | `flows` | `packets`), and paginates conversations directly in SQL, shared via `ConversationsPanel.vue` across Traffic Analytics and Endpoint Detail.
* **Traffic Analytics Multi-View Cockpit (`/bandwidth`)**: Reorganizes the Bandwidth page into 5 URL-addressable views (`Overview`, `Interfaces`, `Conversations`, `QoS`, `Security`) while preserving the `/bandwidth` route.
* **Dashboard & Responsive Navigation**: Severity-first default sorting (`DOWN` $\rightarrow$ `DOWN-UNSTABLE` $\rightarrow$ `UP-UNSTABLE` $\rightarrow$ `UP` $\rightarrow$ `Not monitored`), URL-persisted search/type/location filters, responsive header navigation below `1000px`, collapsible Topology legend, theme-reactive chart palettes (`useChartTheme.js`), and screen-reader chart summaries (`chartSummary.js`).

## Upgrade & Migration Runbook

### From v3.3.2.v (Ephemres layout)

```bash
sudo bash /opt/ephemres/deploy/upgrade.sh
```

The upgrade script creates a pre-upgrade SQL backup in `/var/backups/ephemres/`, synchronizes the codebase, compiles the production Vue 3 bundle, executes native migrations `0014` through `0019` (`python3 -m app.core.migrator upgrade head`), restarts `ephemres-api`, `ephemres-engine` (and `ephemres-flowd` when flow ingestion is enabled), and checks that they are running and the API answers its health check.

If a service does not come up, the script stops with `UPGRADE INCOMPLETE` and a non-zero exit instead of reporting success. The database is already migrated at that point; the message names the pre-upgrade backup and the `systemctl` / `journalctl` commands to inspect the services.

### From v3.2.0 or v3.3.0 (netmon layout)

These releases installed into `/opt/netmon/noop` with `/opt/netmon/venv`, `/etc/netmon`, user `netmon` and `netmon-*` services, so `/opt/ephemres/deploy/upgrade.sh` does not exist yet. Clone v3.3.5 and run its upgrade script; it moves the install to the Ephemres layout:

```bash
git clone --branch v3.3.5 https://github.com/dc8official/ephemres.git ~/ephemres
sudo bash ~/ephemres/deploy/upgrade.sh
```

The script detects the old layout (`/etc/netmon/netmon.env` and no `/etc/ephemres/ephemres.env`) and, after taking the pre-upgrade backup:

* creates the `ephemres` user, `/etc/ephemres/ephemres.env` (the `NETMON_*` keys written again as `EPHEMRES_*` with the same values, so the database password and the key that encrypts alert channel secrets carry over) and `/etc/ephemres/config.toml` (`log_dir` moved to `/var/log/ephemres`);
* builds a new `/opt/ephemres/venv`, migrates the database (`0012` to `0019`), disables the `netmon-*` units and points the existing `/etc/nginx/sites-available/netmon` site at `/opt/ephemres` (the original is saved as `netmon.pre-ephemres`; certificates and local edits are kept);
* starts `ephemres-api` and `ephemres-engine` and checks that the API answers `/api/v1/health`.

Passwords cannot be carried over: v3.2/v3.3.0 stored argon2 hashes. Every user, the admin included, gets a random temporary password listed in `/opt/ephemres/legacy_password_resets.txt` (root only; the upgrade ends with the command to read the admin's), and everyone must change their password at the next login. The install-time `DEFAULT_ADMIN_PASSWORD` is not reused.

`/opt/netmon`, `/etc/netmon` and the disabled `netmon-*` units are left in place. The database itself is migrated, so a rollback means re-enabling the `netmon-*` units and restoring the pre-upgrade backup; remove the old files once the new install is confirmed. A fresh v3.3.5 install followed by `deploy/restore.sh` with a backup of the old server is a supported alternative.
