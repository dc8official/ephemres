# v3.4 Dashboard Data & Design Plan

Merged implementation plan for the Bandwidth (flow), Network Dashboard and Endpoint Detail
pages. It combines three reviews held on 2026-10-26: a data-quality review of what each page
collects and shows, an implementation review of what the fixes touch, and a UI design
critique run against a local build with synthetic data.

Every phase ships on its own version branch and must leave the backend suite green
(`.venv/bin/python -m pytest`) and `npm run build` clean.

## Guardrails

- **API changes are additive.** New fields are optional; existing fields keep their names for
  at least one release. When a value changes meaning (in/out stop absorbing transit traffic)
  the replacement field ships in the same release.
- **One source of flow math.** `app/services/flow_metrics.py` is shared by
  `routers/bandwidth.py` and `services/report_compiler.py`, so the dashboard and the PDF report
  cannot disagree.
- **Real-database tests for SQL and continuous-aggregate changes.** Tests marked `timescale`
  run against a throwaway TimescaleDB (`tests/integration/README.md`). The default suite skips
  them when no database is configured.
- **Characterization first.** The integration tests pin today's numbers, including known-wrong
  ones (the 50/50 transit split, the materialized-only lag). A phase that fixes one of them
  changes the matching assertion in the same commit and says why.
- **New tables are registered everywhere a backup needs them**: `core/restore.py` (table list
  and column-type map), `deploy/RESTORE.md`, and the retention service. Continuous aggregates
  built on a short-retention hypertable use a refresh `start_offset` shorter than that retention.
- **Design tokens only.** New or touched UI uses `var(--…)` tokens from `App.vue` and the
  primitives in `frontend/src/components/ui/`; no new hex values in views. Charts read colors
  through `useChartTheme()`.
- **Check both themes at 1280 px and 800 px** for every changed screen.
- **No new dependencies** (backend runtime stays `uvicorn` + `asyncpg`; frontend additions need
  sign-off).

## Phase 2 — Data model

Code
- Migration 0014: `materialized_only = false` on `flow_hourly_rollups` and `flow_daily_rollups`
  (verified to work inside a transaction on TimescaleDB 2.27).
- Per-cycle probe storage: `PingResult` gains min/max/jitter; new `endpoint_probe_samples`
  hypertable written by the state machine each cycle, with compression, retention and an hourly
  aggregate. Feeds Loss %, 24 h average/p95 RTT, last probe time, RTT trend and the
  correlated view.
- `flow_interface_hourly_rollups` (sum + busiest minute) for windows beyond 7 days; p95 and peak
  utilization; rate divides by the time actually covered.
- Exporter health: last flow time and flows/s per exporter; unmatched exporters get
  `flow_count`.

Design (D2)
- Endpoint detail status header: state, current RTT and loss, time in state, last probe;
  monitoring/active toggles become labelled switches.
- RTT chart on a real time axis with min/max band and loss markers; correlated view as two
  charts sharing one time axis.
- Dashboard table sparklines; interface cards with p95/peak markers and a "Set speed" state.

Phase 2 decisions and notes
- Probe history retention (decided 2026-10-26): raw samples 30 days, hourly aggregate 365 days.
  Roughly 1.4 M rows/day per 1,000 endpoints, about 12 MB/day once compressed.
- Interface p95 counts idle minutes as zero; on the 30-day window it is over hourly averages
  (continuous aggregates cannot hold percentiles). Peaks are always the busiest minute.
- Found and fixed: without `CAP_NET_RAW` the raw ICMP tier reported every probe as lost instead
  of falling back to the unprivileged socket. Production units grant the capability; dev runs and
  containers that drop it now fall back (logged once).
- Restore rebuilds aggregates from restored source rows, so aggregate history older than the
  source retention is not restored (documented in `deploy/RESTORE.md`).

## Phase 4 — Decisions required first

### WAN interface role and edge totals (done, 2026-10-26)

- Each `flow_interface_aliases` entry takes `role: "wan" | "lan"` (default `lan`; legacy name
  strings are `lan`). Both interface editors (Traffic → Interfaces and Endpoint Detail) have a
  Role column and share `utils/interfaceConfig.js`, so a save keeps every field.
- `services/wan_edge.py` lists WAN interfaces (`jsonb_path_exists` on the alias map, live
  endpoints only) and sums their interface rollups. Overview: `wan_in/out_bps|pps`,
  `wan_interfaces_count` and `wan_links` (per link: rates, utilization, share of WAN bytes).
  `traffic-series?wan_only=true` returns the WAN sum per bucket and falls back to the normal
  series when nothing is marked. PDF bandwidth report: a network-edge row and a WAN tag on
  interface rows.
- UI: WAN in/out tiles and a WAN links card lead the Overview once a link is marked; the chart
  defaults to "WAN edge" with an "All flows" toggle (`totals=all` in the URL). Fleet scope with
  two or more exporters notes that ingress/egress/transit count traffic once per router.
- Found and fixed on the way:
  - Saving either editor gave every "Not set" interface a 1 Gbps speed. Speed is now optional
    in `InterfaceConfig` and the editors have a "Not set" preset.
  - The Endpoint Detail editor would have dropped roles on save.
  - Three copies of the alias normalizer are now one (`schemas.bandwidth.normalize_interface_aliases`).
    The exporter list's copy would 422 on a stored `null` speed. Legacy name-only aliases now
    report `speed_mbps: null` instead of a guessed 1000, matching how utilization treated them
    since Phase 1.

### NetFlow route augmentation (design, 2026-10-26)

Traceroute stays the route of record: it builds the baseline routes, drives RCA and draws the
topology. NetFlow adds what traceroute cannot see: the path real traffic takes through each
exporting router, observed every minute instead of nightly. Today no flow data reaches
`baseline_route.py`, `rca_engine.py` or the topology; the parsers also drop the next hop
(v5 unpacks it and discards it; v9 and IPFIX do not decode it).

What it fixes in traceroute:

| Traceroute limit | What flows add |
|---|---|
| Path from the Ephemres server, not from users | Each exporter reports where it forwarded real traffic |
| Silent hops (`* * *`) | An exporting router reports its own egress interface and next hop |
| ECMP: each probe may take a different path | Every path carrying traffic, with its share |
| Return path invisible | Return traffic arrives as separate flows, so asymmetry shows |
| Runs nightly or on failure | A path change is seen within minutes and triggers a targeted re-trace |

Coverage limit: only routers that export flows, and only traffic that crosses them. Elsewhere
traceroute remains the only source, and nothing below may override it.

#### 1. Next-hop decoding

- v5: keep the unpacked `nexthop` in the flow dict.
- v9: decode field 15 (`IPV4_NEXT_HOP`) and 62 (`IPV6_NEXT_HOP`).
- IPFIX: decode IE 15 (`ipNextHopIPv4Address`) and 62 (`ipNextHopIPv6Address`).
- BGP next hop (field / IE 18) is out of scope: it names the BGP peer, not the next router.
- `0.0.0.0` / `::` (delivered locally, or not routed) and a missing field are stored as null.
- The collector adds `nh` to the stream entry; the aggregator treats a missing `nh` as null,
  so entries written before the upgrade still parse.
- `docs/netflow-guide.md`: per vendor, how to include the next hop in the export template.

#### 2. Path observations table

New plain table `flow_path_observations` (migration 0017; small, so not a hypertable). It
holds one row per distinct forwarding choice an exporter made for traffic to or from a
monitored endpoint:

| Column | Notes |
|---|---|
| `exporter_id`, `endpoint_id`, `direction` (`to` / `from`) | The endpoint is the monitored side of the flow |
| `in_if`, `out_if`, `next_hop` (inet, nullable) | The forwarding choice |
| `first_seen`, `last_seen` | |
| `bytes`, `flow_count` | Running totals since `first_seen` |

- Primary key: `(exporter_id, endpoint_id, direction, in_if, out_if, next_hop)`, with a
  `COALESCE` unique index because `next_hop` can be null.
- Written by the aggregator in its existing 10-second flush, as one batched upsert that
  advances `last_seen` with `GREATEST`.
- Only flows with a known exporter (not `SENTINEL_UUID`) and a monitored endpoint on one side
  are written.
- Expected size: exporters × monitored endpoints × 1–3 paths each, so thousands of rows, not
  millions. The conversation table is not widened.
- Rows whose `last_seen` is older than the retention window are pruned daily. Suggested
  retention: 30 d.
- Backup and restore: confirm that `core/restore.py` handles the new table, and add a test.

#### 3. Change detection and targeted traceroute refresh

- **Detector (aggregator, in memory).** For each `(exporter, endpoint, direction)` it tracks
  the dominant `(out_if, next_hop)` of each complete minute, by bytes. It reports a change only
  when a different path is dominant for N consecutive minutes (default 3) and the old path has
  stopped carrying traffic.
- **ECMP.** Two or more paths that each keep at least 20 % of bytes are recorded as
  load-balanced, not as flapping. Thresholds live in settings.
- **On a change**, the aggregator publishes `ROUTE_HINT` through the existing EventBroker, the
  same path as `STATE_TRANSITION`. The payload carries the endpoint, exporter, and old and new
  interface and next hop.
- **In the backend**, `telemetry_relay` subscribes and puts the endpoint on the existing
  `discovery_route_queue`, deduplicated by `discovery_in_progress`.
- **Guards:**
  - Only endpoints that are UP and have `enable_scheduled_discovery` are re-traced. The
    baseline is the last-known-good path that RCA compares against, so it must never be
    overwritten during an outage.
  - Per-endpoint cooldown, suggested 15 min.
  - A global cap on targeted traces per minute, so a core-link failover cannot set off a
    traceroute storm.
- **Records:** each change is written as an event ("Route change seen in flows: R1 now sends
  traffic for X out Gi0/2 via 10.0.0.6, was Gi0/1 via 10.0.0.2") and sent over SSE. Whether it
  also raises an alert is an open decision (see below).

#### 4. Topology confirmation

For each baseline route, the hop at position k is matched to an exporter when its IP equals
the exporter's IP or one of its `flow_exporter_ips`. A traceroute shows the router's ingress
interface address, so admins may need to add interface IPs as aliases. The edge from hop k to
hop k+1 is then classified from the observations for `(that exporter, endpoint, 'to')` seen in
the last 15 min:

| Status | Rule | Display |
|---|---|---|
| `confirmed` | Active next hop equals the hop k+1 IP | Solid line, "confirmed by traffic" |
| `differs` | Active next hop is something else | Warning style; tooltip shows both paths |
| `inferred` | Hop k+1 is `*` and the next hop is known | Dashed node and edge, labelled "from flow data" |
| `unknown` | No exporter match or no recent observations | Unchanged; never shown as a disagreement |

- `topology_manager` computes the status when it builds the graph and refreshes it every
  5 min. No request reads the observations table.
- The topology payload gains `flow_status` per edge. `TopologyMap` adds a line style and a
  legend entry for it.

#### 5. RCA hint

When an RCA runs for endpoint X, it adds a "Flow evidence" block. The block lists, for each
exporter:

- when traffic to and from X was last seen;
- the interface and next hop that traffic last used;
- whether any traffic was seen in the last 5 min. If traffic is still flowing while probes
  fail, the fault is on the probe path or ICMP is filtered.

It also flags any route change found in the 15 min before the failure.

- The block is stored with the incident, next to the baseline snapshot, and shown in
  `EndpointRcaDetail`.
- It is evidence only. The RCA verdict logic does not change.

#### Order, tests and open decisions

- **Order:** 1 and 2 (data), then 5 (it only reads the table), then 3, then 4.
- The per-link view from the WAN-role item builds on the same interface data and can ship with
  2.
- **Tests:**
  - parser tests for the next-hop fields in each version, including null and missing values;
  - the aggregator upsert, plus an integration test on the table;
  - detector unit tests: steady path, a real switch, ECMP, flapping below N minutes;
  - relay to queue: the UP-only guard, the cooldown and the global cap;
  - edge classification for all four statuses;
  - the RCA hint, with and without flow data.
- **Open decisions:**
  - observation retention (30 d suggested);
  - whether a route change raises an alert or only records an event;
  - the default N, ECMP share, cooldown and global cap values.
